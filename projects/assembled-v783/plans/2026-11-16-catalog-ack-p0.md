# P0 v783 — true catalog acknowledgment after durable storage (TDD plan)
Date: 2026-11-16. Branch from workshop/main@c0d10a58. Do NOT deploy customers.
## Read-only discovery, not yet a demonstrated customer incident
In the assembled browser `app/docs/mock-backend.js`, `_fetchInterno` returns HTTP responses from mutations and its `finally` invokes `guardarEstadoLocal()` without awaiting its possible Promise. The existing `POST /api/ubicaciones` returns `J(nueva)` before that `finally`. The non-strict save can fail or reject under storage errors or cross-tab conflicts. Thus HTTP 2xx does **not**, on inspection, prove durable save. The WebKit tab test independently checks cold-read after 2xx and failed in the prior full audit once; causality is NOT established. This is a precise hypothesis worth RED instrumentation, not permission to overwrite a shop.
## Minimal Ponytail/Superpowers plan
1. Reuse `tab-session-handoff.test.js` real fixture, existing `seed/context/ownerLogin`, no new harness. Add a **single browser test** with synthetic rack and injected `OCEstadoAB.guardarAhora=false` and `OCEstadoIDB.guardar=Promise.resolve(false)`. Test that non-durable creation does not return an HTTP 2xx; verify no new rack after cold reopen and clean up monkey patches. Establish RED using official WebKit in GitHub Actions, keep log.
2. Read existing strict-sale rollback and `guardarEstadoLocal(true)` contract before modifying backend. Do NOT globally await `finally` or change money paths. Avoid false-negative reply if the store can still commit. If a complete correct rack-only fix requires a shared API persistence refactor, document the verified gap and keep runtime unchanged rather than half-fix.
3. Validate no duplicate rack or movement on retry and no false ACK on storage abort/cross-tab CAS conflict, including Chromium/WebKit, cold reload and restored IDB. Preserve all prior local-first behavior.
4. Run focused browser, 585 CI target, full comparison and review; merge only proven GREEN, with reversible diff. Never edit customer data, PIN, issuer, production SW/Pages or relay.
## Admission criteria
A success response means the rack exists in read-back-verified local durable storage, with no overwritten peer rack. Rejections do not silently persist an unconfirmed rack later. No UI reset on unverified writes. Stock is derived from events, never fixed to a snapshot value.
